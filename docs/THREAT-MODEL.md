# Ascend Foundation Threat Model

**Status:** Foundation baseline approved on 2026-07-18; feature-specific threat models and named gates remain required
**Last updated:** 2026-08-05

## Purpose and scope

This document defines the security assumptions and mandatory controls for Ascend's individual v1 and its organization-ready foundations. It covers the local shell and engine, database and files, recordings, activity capture, provider calls, personal work integrations, OAuth, imports, MCP/local API access, LLM processing, and future workspace isolation. It also records OD-20's future local screenshot/vision direction and proposed OD-19 controls for future agents, skills, typed tools, context disclosure, approvals, durable runs, external-agent providers, and background triggers; those controls are requirements for later specifications, not claims of implementation.

It is not a claim that unimplemented controls already exist. Each control becomes a testable requirement when the related feature is specified.

## Assets

- Provider credentials and connector tokens
- Google, ClickUp, Asana, and future Outlook access/refresh tokens, OAuth state, and provider account identity
- Dictation and meeting audio
- Transcripts, summaries, notes, commitments, and imported documents
- Application/window activity and inferred productivity information
- Personal and future workspace memory
- Actor, device, membership, permission, and workspace identifiers
- Tenant-account identifiers and separate work-entity identifiers
- Voice profiles, embeddings, diarization labels, speaker-identity evidence, and corrections
- Future health, wellbeing, habit, energy, reflection, and spiritual-practice data
- Audit records, corrections, and provenance
- Imported assigned tasks, calendar events, source links, attendee identity, and sync metadata
- Installer, update packages, native helpers, and dependency lockfiles
- Future model/runtime binaries, model weights, manifests, licenses, hashes, execution receipts, and hardware-capability data
- Future raw screenshots, thumbnails, temporary frames, visual-context indexes, derived visual observations, capture policies, exclusions, and screenshot/model execution receipts
- Future agent profiles, skill manifests/resources/versions, tool schemas, workflow definitions, trigger policies, run ledgers, checkpoints, approvals, execution receipts, evaluation results, and cost budgets
- Context-disclosure records, trust labels, external-agent identities, provider route policy, and skill/agent ownership or publication metadata

## Trust boundaries

1. **Electron renderer to shell main process:** renderer content must not receive engine secrets or unrestricted native access.
2. **Shell to Python engine:** loopback communication still crosses a process boundary and requires authenticated, validated messages.
3. **External MCP/API client to engine:** each client may be malicious, compromised, over-permissioned, or confused about workspace scope.
4. **Engine to SQLite/files:** every access must pass through the data-access and media-storage boundaries with explicit workspace/owner context.
5. **Engine to cloud provider:** audio, text, metadata, credentials, responses, cost, retention, and availability leave local control.
6. **Imports/retrieval to memory and LLM context:** documents and transcripts may contain malicious instructions, oversized payloads, or poisoned content.
7. **LLM output to product behavior:** model output is probabilistic untrusted data, not authority or executable intent.
8. **Windows capture and clipboard interfaces:** device churn, focus changes, other applications, and clipboard contention can cause disclosure or incorrect actions.
9. **Future personal-to-organization sharing:** an incorrect tenant/workspace scope or role check could disclose one person's private work to another member or manager.
10. **Build and update supply chain:** dependencies, install scripts, donor files, native binaries, and update artifacts can execute with user privileges.
11. **Tenant account versus memory entity/context:** confusing any personal or professional memory subject with an account could turn ordinary memory references into authorization decisions. An organization/client inside memory is the highest-confusion example, not the only case.
12. **Desktop to system browser/provider OAuth callback:** callback injection, state replay, wrong-account binding, embedded secrets, or malicious redirects could expose a provider account.
13. **Engine to task/calendar providers:** authorized MCP servers and APIs return untrusted content/tool metadata, partial pages, rate limits, revocation, schema drift, and records belonging to multiple users/workspaces.
14. **Desktop/system browser to Ascend connection service:** the approved confidential OAuth boundary becomes a high-value secret, token, callback, abuse, and availability boundary even though provider content must not pass through it by default.
15. **Inbound Ascend MCP versus outbound provider MCP:** conflating client grants, tool registries, or audit context could let one integration inherit another integration's authority.
16. **Engine/native audio adapter to Windows devices:** stale identities, callback races, partial mute failures, device hot-plug, or a crashed controller can capture from the wrong microphone, leave playback muted, unmute user-owned state, or falsely report that capture is safe.
17. **Electron display topology to overlays/windows:** mixed DPI, negative coordinates, display removal, or stale saved bounds can hide the recording indicator or place controls outside every current work area.
18. **Engine to future model/runtime worker:** dependency-heavy or native code can crash, hang, exhaust resources, return malformed data, or attempt to inherit database, credential, filesystem, MCP, or workspace authority.
19. **Model/runtime acquisition and activation:** weights, executables, DLLs, manifests, converters, and remote model code are supply-chain inputs that may be malicious, corrupt, incompatible, unlicensed, or replaced after review.
20. **Local/cloud execution router:** a fallback or policy bug could transmit data that the user required to remain local, misrepresent which model/service ran, or hide cost and retention changes.
21. **Future calendar-triggered cloud meeting bot:** stale or malicious event data, recurrence/time-zone drift, duplicate scheduling, wrong-room admission, consent gaps, provider identity confusion, or partial artifacts can record or attribute the wrong meeting.
22. **Future speaker identity and sensitive personal domains:** probabilistic identity evidence can misname a person, while generic search, organization, API, MCP, export, AI, or diagnostic paths can expose voice, health, wellbeing, energy, or spiritual-reflection data.
23. **Skill registry to run coordinator:** malicious or changed skill instructions, resources, dependencies, or scripts can inject instructions, exfiltrate context, request excessive tools, or expand through recursive composition.
24. **Context broker to model or external agent:** overbroad, wrong-workspace, wrong-data-class, or retention-incompatible disclosure can expose private data even when the resulting answer is harmless.
25. **Model/external agent to typed tool gateway:** probabilistic or prompt-injected output can invent tools, alter targets, launder approval, smuggle arguments, or attempt a side effect outside the user's intent.
26. **Scheduler/event inbox to run coordinator:** duplicate, forged, stale, or attacker-controlled events can trigger unintended, repeated, or out-of-hours work without an interactive user present.
27. **Run ledger and approval state:** a crash, timeout, replay, modified proposal, cross-run approval, or corrupted checkpoint can duplicate writes or resume with stale authority.
28. **Ascend to external ChatGPT/Claude or other agent surface:** browser sessions, private endpoints, excessive context, wrong external agent identity, provider retention, or weak cancellation can expose credentials or execute against the wrong target.
29. **Future Windows screen capture to local screenshot storage:** a frame can contain passwords, one-time codes, private messages, financial/health information, confidential work, another monitor, or the wrong application before a detector can classify it.
30. **Encrypted screenshot store to local vision/OCR worker and memory:** overbroad handles, worker network access, cache/temp leakage, model extraction errors, wrong-workspace persistence, backups, or deletion gaps can expose raw pixels or convert them into incorrect durable context.

## STRIDE summary

- **Spoofing:** local client, future member/session, trigger source, publisher, external agent, or service-principal impersonation. Mitigate with scoped credentials, audience binding, immutable identity, and explicit actor/client/run context.
- **Tampering:** modified database, media, imports, IPC messages, models/runtimes, skills, tool schemas, approvals, checkpoints, or updates. Mitigate with validated interfaces, checksums, pinned manifests, immutable versions, quarantine, signatures where applicable, migrations, rollback, and append-only attempt/audit events.
- **Repudiation:** denial of sharing, context disclosure, external reads/writes, permission changes, approvals, or agent actions. Mitigate with actor/client/workspace/run-aware proposals, decisions, receipts, verification, and audit records.
- **Information disclosure:** cross-tenant/workspace/data-class context, external-agent handoff, malicious skill, silent cloud fallback, logs, prompts, exports, clipboard, provider retention, or plain local storage. Mitigate with least privilege, a minimum-context broker, trust labels, explicit locality and provider policy, field allowlists, redaction, explicit sharing, and an approved at-rest posture.
- **Denial of service:** oversized imports, recursive agents/skills, token/cost loops, duplicate triggers, provider retries, audio/device failures, inference OOM/thermal pressure, worker hangs, or database scans. Mitigate with preflight checks, depth/concurrency/cost/time limits, cancellation, pagination, bounded queues, and visible degradation.
- **Elevation of privilege:** role confusion, UI-only permission checks, prompt injection, approval laundering, permission-bearing skills, arbitrary model code, overbroad worker/MCP capabilities, or unscoped repository methods. Mitigate with centralized authorization below prompts and UI, typed execution, exact approval binding, worker isolation, local tool allowlists, separate trust domains, and adversarial tests.

## Data and privacy invariants

- Personal activity, private meetings, dictations, notes, and memory are not organization-visible by default.
- Every owned or shareable record has explicit owner, workspace, and visibility semantics.
- Tenant accounts and all personal/professional memory entities or contexts have separate models and identifiers; memory content never grants authority.
- Organization analytics never expose private individual timelines or create employee rankings, productivity leaderboards, or hidden monitoring.
- Remote telemetry is off by default; local diagnostic logs do not contain prompts, transcripts, audio, window content, or secrets.
- Future screenshot capture is off by default, visible, pauseable, target-scoped, exclusion-aware, and retention-bound. A local-only design is not described as secret-proof.
- Raw screenshots, thumbnails, temporary images, and derived visual context require proven at-rest protection before real use and remain personal/restricted data classes by default.
- Raw screen pixels never use an implicit cloud fallback and are denied from organization access, general API/MCP/export, diagnostics, support bundles, and unrelated AI context by default.
- Personal provider connections and imported records remain private to the owner's personal tenant/workspace unless deliberately shared under a future approved feature.
- Provider access is read-only in initial v1; Ascend cannot create, update, complete, reassign, or delete provider tasks/events.
- Every imported provider record has a connection, namespaced external ID, source, fetched/last-seen time, and visible stale/deleted state.
- No reusable Google, Microsoft, ClickUp, Asana, or other confidential client secret is embedded in a distributed desktop artifact.
- Provider user credentials are isolated per actor, tenant, destination workspace, provider account, and environment; no grant is shared implicitly.
- Ascend's inbound MCP/API grants and outbound provider MCP/API grants are separate and non-transferable.
- Provider-advertised capabilities never expand Ascend permissions; initial-v1 can invoke approved reads only.
- Voice embeddings, provider secrets, and excluded content are never serialized through general API, MCP, export, analytics, or logging paths.
- A user-approved local-only request never becomes a cloud request implicitly; the actual adapter, model/service, locality route, and disclosure policy are recorded.
- Model/runtime workers never receive direct database, credential-store, inbound/outbound MCP, or unrelated tenant/workspace access.
- Model/runtime artifacts are treated as executable supply-chain inputs even when they are described as weights or configuration.
- Diarization labels are not identities. Unknown is a valid speaker state, and names require typed evidence, confidence, and correctability.
- Health, wellbeing, voice-identity, energy, and spiritual-reflection data are not included in work search, organization access, API, MCP, export, diagnostics, or unrelated AI context by default.
- External writes remain pending until accepted by an authorized person.
- Skills, prompts, tool descriptions, retrieved content, and model output are never sources of authority.
- No model or external agent receives raw connector credentials; the typed gateway executes under a run-scoped grant.
- Every future agent run has explicit actor, tenant, workspace, purpose, data classes, versions, provider/locality route, budget, disclosure, approval, receipt, and terminal-state records.
- Personal skills, agents, schedules, runs, and evaluation history are not organization-visible by default. Sharing a skill does not share its owner's prompts, memory, runs, connector grants, or credentials.
- An approval cannot be reused after its exact operation, target, arguments, disclosure, actor, run, policy, risk, cost, or expiry changes.
- A timeout or crash is an uncertain execution state, not evidence that a provider write failed; reconcile before retrying.
- Scheduled and event-triggered runs have no ambient interactive authority and never use silence as consent.
- Ascend model-provider calls, inbound external-AI clients, and outbound external-agent providers have separate credentials, context grants, and audit namespaces.
- Browser/UI automation, consumer-session cookies, and private endpoints are not approved external-AI control paths.
- A member leaving an organization must not lose personal data or retain organization-owned data without an explicit export policy.
- Public claims must match implemented behavior, particularly storage encryption, deletion, cloud processing, provider retention, and recording consent.

## At-rest storage decision and residual risk

OD-03 Option 1 was approved on 2026-07-19. Plain SQLite, recording files, and future screenshot assets expose sensitive content to disk theft, backups, malware, and any process running as the signed-in Windows user. A loopback API token does not protect against same-user malware, and DPAPI protects provider keys but not an otherwise plain database, audio file, or screenshot.

Until encryption is implemented and proven:

- Plain storage may contain synthetic development data only.
- Do not capture real meetings, real work activity, or private memory into the new application.
- Do not make claims that the database or recordings are encrypted.
- Keep database and media access behind single replaceable boundaries so the approved encryption design does not spread across the codebase.

Even with encryption at rest, Ascend cannot protect data from malware or another person operating inside an already unlocked Windows account. This residual risk must be stated honestly.
